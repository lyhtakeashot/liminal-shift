## 0. 两条硬约束（机制决定，不能妥协）

### 0.1 内外严格 1:1

本作核心玩法：切到同一地点的不同年代。

| 年代 | 这块地上有什么 |
|---|---|
| 1926 | 空地 |
| 1951 | 陆家老屋 |
| 1976 | 陆家只剩地基 |
| 2001 | 停车场 |
| 2026 | 超市扩建 |

玩家站在 1926 的空地按 Shift，**人出现在 1951 那栋房子内部** —— 不需要找门，**时间是门**。

- 外观占地必须**精确等于**内部可行走区 + 墙厚
- 差一格，切时间就卡墙里
- 不学星露谷「内部比外部大」（它外观 9×5、内部 10×7）—— 那会直接毁掉这个机制

### 0.2 房型不是矩形

这是用户明确要求：要 **L 形、凹形、四合院**，矩形只是灰盒阶段的临时做法。

**做法：翼组合法**（星露谷同款 —— 木匠铺是 L 形，社区中心是凹形带塔）

> 一栋房子 = 若干矩形**翼**的组合。
> 每翼一个矩形，屋脊沿该翼长轴。
> 两翼相接处墙体自动消解成连通，跨翼不需要开门洞。
> 南翼压北翼檐（绘制顺序：按 y 从小到大）。

## 1. 基础规格

| 项 | 值 |
|---|---|
| 一格 | **32 × 32 px**（TILE 2026-11-22 从 16 改成 32，唯一定义点 `scripts/house_shape.gd:13`） |
| 内部分辨率 | 1280 × 720（40 × 22.5 格） |
| 缩放 | fractional（1080p=1.5× / 1440p=2× / 4K=3×），`project.godot` `stretch/mode="canvas_items"` + `scale_mode=0` |
| 视角 | 2D 俯视 3/4 |
| 光源 | 统一左上来，硬边色块，不用渐变 / 抖动 / 抗锯齿 |
| 描边 | 不描黑边，靠色块明暗分界 |

### 1.1 尺寸基准（对齐星露谷，美术必读）

**1 格 = 32 × 32 px，是所有尺寸的锚点。**（星露谷原版是 16×16；我们 2026-11-22 起用 32×32——网格数照抄星露谷口径，像素翻倍给美术留细节。）星露谷官方 modding 论坛版主 mouse 原话：
> "Stardew sprites are (mostly) 16x16 yes, with things like an NPC overworld sprite being 16x32, or individual portrait frames being 64x64."
> （来源：https://forums.stardewvalley.net/threads/sprite-size-first-time-modding-sv.7128/）

据此定标：

| 对象 | 尺寸 | 折合格 |
|---|---|---|
| 基准 tile / 棋子 / 作物 / 小道具 | 32 × 32 px | **1 × 1 格** |
| **玩家 / NPC 行走图** | 32 × 64 px | **宽 1 格、高 2 格** ← "人是两个最小单位" |
| 头像（如需要） | 64 × 64 px | 2 × 2 格 |
| 建筑 | 32 × 32 网格对齐 | 见 §2 翼定义 |

**为什么先定这个锚点**：B 站教程 BV1CW4y1s7fC 的热评（UP 主点赞）指出——先给最小 item 定尺寸，不然后面加更小的道具时整个比例尺会失真。星露谷自己也有妥协：农舍外观 9×5 格、内部 10×7 格，我们**不学**这条（见 §0.1）。

> 注意：星露谷的家具 / 装饰物不是统一 16×16，而是按"占地格数"分级（台球桌 3×2、画 1×1 贴墙、酒桶 1×1）——这是 §4.6 要讲的另一套规则，不要和"基准 tile"混为一谈。

## 3. 沈家五帧演变（关卡设计的核心）

**每代加一翼，旧翼不拆。** 玩家在时间轴连按 W，看到的是同一块地「长出来」——这是搜证本身。

| 帧 | 房型 | 翼数 | 材质 |
|---|---|---|---|
| 1926 | 一字形（土坯） | 1 | mud |
| 1951 | L 形（青瓦） | 2 | tile |
| 1976 | 凹形（灰瓦两厢） | 3 | slate |
| 2001 | 四合院（灰瓦） | 4 | slate |
| 2026 | 全拆 → 超市压在原址 | — | — |

> 这就是「继承场景数据」比「全量复制」省的原因（HANDOFF §3.3）：
> 五帧共用同一批翼，只有增量。

## 4. 交互 / 碰撞规则

| 轴 | 玩家是否有碰撞体积 | 行为 |
|---|---|---|
| **空间轴** | 有 | 撞墙停住，可沿墙滑（AABB 分轴推进） |
| **时间轴** | **无** | 目标帧的墙不阻挡；但目标帧的墙若压在玩家**当前位置上**，则推不过去（「顶住了」） |

判定走纯数据矩形（`scripts/frame_data.gd`），不是物理引擎。原因见 HANDOFF §3.3 / §3.4：
- `visible=false` 不关碰撞
- 禁用中的 `CollisionShape2D` 无法做目标帧重叠检测

**对美术的直接影响**：每栋房子必须输出精确的**墙体矩形表**（每翼一圈墙 + 门洞位置），不能只有一张 PNG。

> **这条已经在做了。** `_ref/houses/houses_data.json` 里每栋都有 `wings`（屋本体）+ `partitions`（隔墙线段）+ `doors` + `gate`，
> `gen_all_houses.py` 的 `build_grid()` 会把它们展开成字符网格、`check_all()` 校验合法性。
> **美术只要照 `_ref/art/<帧>/<id>.png` 画，墙和门的位置就已经是确定的了。**
> 详见 `docs/HANDOFF-VILLAGE.md`。

> **楼层除外。** 「在二楼推时间、过去只有一层、人落到屋顶上」这条路，
> 现在的判定是「目标帧该坐标有没有 solid」，所以**根本不会发生，会被顶住**。
> 要做得改成「查目标帧该坐标不高于当前高度的最高可站表面」——方案在 §8，用户 11/19 降到 P3。

## 4.5 室内呈现与物件实体（已验证可实现）

**结论：不用 3D。用 2D 分层 + 深度排序就能画出"看得见内侧墙"的室内。**
验证脚本：`_mdtest/interior_check.gd`（纯逻辑）+ `_mdtest/interior_canvas.gd`（绘制原型），已跑通。

### 4.5.1 三层结构

每栋房子拆成三层，**共用同一占地**（这就是内外 1:1 的直接体现）：

| 层 | 内容 | 屋外 | 屋内 |
|---|---|---|---|
| `base` | 地板 + 墙内侧 | ✅ | ✅ |
| `roof` | 屋顶（独立层） | ✅ | ❌ 隐藏 |
| `props` | 家具实体（独立对象） | 不画 | ✅ |

**屋顶显示条件：玩家不在建筑占地矩形（`wings`）内时画屋顶，进去就不画**（与轴无关，精确判定，**不做 α 渐变**）。完整规则见 §4.8.4。
这样玩家在空间轴从门走进屋也能看到室内；同时它和时间轴"世界变透明"的美学一致。

>  reasons：如果只在时间轴淡出屋顶，玩家用空间轴进门时会撞见一整块屋顶盖在头上。
>  按位置判定更自然，也更好实现（一个矩形包含判定）。

### 4.5.2 墙的画法（俯视 3/4 的行业约定）

观察者在东南方向，所以：

- **北墙、西墙**：画全高内侧面（朝向室内，可见）
- **东墙、南墙**：只画矮内侧面（能看出是墙，但不挡住家具和玩家）

如果四面都画全高，南侧墙会把整个室内盖住 —— 这是俯视游戏的标准取舍。
（如果美术坚持四面全高，技术上也能做，但要接受家具被挡；不推荐。）

> 已实现：北/西墙全高、东/南墙半高（TILE/2），见 `docs/DECIDE-stardew-visual.md` D3。

### 4.5.3 深度排序（伪 3D 遮挡）

玩家和家具按 `y` 坐标排序后绘制：

- 玩家站在家具**下方**（y 更大）→ 玩家挡住家具
- 玩家站在家具**上方**（y 更小）→ 家具挡住玩家

这让玩家能"绕到桌子后面"，是室内探索有立体感的关键。实现成本极低（一次 sort）。

### 4.5.4 物件实体 ≠ 一张图

家具必须同时是**数据和图**：

```json
{
  "id": "mill_stone",
  "name": "石磨",
  "pos": [5, 7],          // 格子坐标
  "size": [2, 2],         // 占地格数（参与碰撞）
  "reach": 2.0,           // 检视距离（格）
  "texture": "mill.png",
  "text": "上磨盘刻着：沈氏丰源 · 一九五七"
}
```

`pos` / `size` / `reach` 是机制数据，`texture` 是美术，`text` 是叙事 —— 三者分离。
**没有数据的家具只是贴图，玩家检视不到，等于白画。**

### 4.5.5 室内必须有的家具（按房型）

| 房间 | 家具 |
|---|---|
| 一字形（陆/周） | 床铺、灶台、桌子、柜子 |
| L 形（沈 1951）右翼 | 灶间：灶台、水缸、柴堆 |
| 凹形（沈 1976） | 北堂：桌、椅、神龛；西厢：床、柜；东厢：储物；天井：水缸 |
| 四合院（沈 2001） | 加南倒座：账桌、箱柜；天井：石磨 |
| 磨坊 | **石磨（核心）**：上磨盘刻「沈氏丰源 · 一九五七」 |

> 磨坊的石磨是 A5 超市门厅那件道具的原型 —— 同一件东西跨七十年。
> 这是三段式线索里"铁证"的物证锚点，必须做出辨识度。

## 4.6 装饰物尺寸分级与搜证交互

### 4.6.1 星露谷的真实规则：尺寸是数据，不是画出来的

星露谷每件家具都有一个写死的**占地格数（footprint）**，放置时按 tile 网格吸附，能放显绿格、不能放显红格。
**没有"某类东西必须几格"的全局公式**——是逐件手工定的。
来源：[Furniture 家具表（含每件的 Size）](https://teemo.dev/game-design/stardew-valley/wiki/furniture/) / [Stardew Valley Wiki: Furniture](https://stardewvalleywiki.com/Furniture)

实测尺寸分布（均折合 1 格 = 16px）：

### 4.6.3 交互 = 数据，不是美术

物件分三层，**只有后两层进数据**：

| 层 | 有图 | 有数据 | 玩家能检视 | 美术要求的交付 |
|---|---|---|---|---|
| 纯装饰 | ✅ | ❌ | ❌ | 只画图，随便放 |
| 可检视物件 | ✅/❌ | ✅ pos/size/reach/text | ✅ | 图按 §4.6.2 分级标注尺寸 |
| 证物 | ✅/❌ | ✅ + clue/frames | ✅ + 记入归档 | 同上，**命名即 id** |

**关键纪律**（对应 m00771「图太多只能一批批放入」）：
- **先填数据，后补图**：有数据没图 → 占位块 + 文字照常能检视；有图没数据 → 只是贴图，美术白画
- 图名 = id（如 `mill_stone.png`），数据团队靠文件名对号入座，不用猜
- 交付清单里标格数（如 `painting_1x2.png`），不让数据团队目测

### 4.6.4 证物数据格式（2026-11-19 重设计：位置/外观/内容全部按帧给）

**为什么改**（用户 m01037）：旧版 `pos`/`texture` 是全局的、只有 `text` 按帧，无法表达两件真会发生在故事里的事——
① 同一件东西在不同帧位置不同（尸体被换位置）；② 同一位置同一件东西新旧程度不同（日记发黄、有污渍、多了内容）。

新结构：**证物的身份（id/name/clue）全局唯一；出现与否、在哪、长什么样、写着什么，全部挂在 `states` 的帧键下**。

```json
{
  "id": "corpse_road",
  "name": "井边人影",
  "clue": "lu_jingzhi_body",
  "axis": "both",
  "states": {
    "a2": {
      "pos": [12, 9], "size": [1, 1], "reach": 2.0,
      "texture": "body_old.png",
      "text": "井台边浮着一个人，脸朝下。"
    },
    "a3": {
      "pos": [18, 14], "size": [1, 1], "reach": 2.0,
      "texture": "body_old.png",
      "text": "地基坑里压着一个人，已经看不清脸。"
    }
  }
}
```

```json
{
  "id": "shen_diary_true",
  "name": "沈万山真本",
  "clue": "shen_true_ledger",
  "axis": "both",
  "states": {
    "a3": {
      "pos": [4, 6], "size": [1, 2], "reach": 1.5,
      "texture": { "base": "diary.png", "overlays": [] },
      "text": "民国十五年十一月十七，晴。陆氏子过河在闸下。"
    },
    "a5": {
      "pos": [4, 6], "size": [1, 2], "reach": 1.5,
      "texture": { "base": "diary.png", "overlays": ["aging.png", "stain.png"] },
      "text": "民国十五年十一月十七，晴。陆氏子过河在闸下。　（后页另有一行小字：闸下无人捞）"
    }
  }
}
```

字段说明：

- **`states` 按帧键 `a1`–`a5`**：某帧没有这个键 = 该物这年不存在（不用写 `visible:false`）。同一 id 在不同帧 `pos` 不同 = 东西被移动过；`pos` 相同但 `texture`/`text` 不同 = 原件老化/添了内容
- **`texture` 两种写法**：字符串 = 一张完整图；对象 `{base, overlays, tint?}` = 基础图 + 逐张叠加的旧化层/污渍层。**叠加层缺文件时静默跳过、保留 base**（对应 m00771「图一批批加」）；base 也缺 → 占位块 + 文字照常可检视
- **`size` 与 `reach` 分离**：`size` 管碰撞/占地，`reach` 管"站多近能检视"。贴墙壁画 `size=[0,0]` 但 `reach=1.5` 照样能读 → 星露谷"画能看但不占地"的机制映射
- **`axis`**：默认 `both`；写 `"space"` 表示只能在空间轴检视（用于"墙里/井下"这类时间轴穿墙会穿帮的物件）
- **`clue`**：对应归档表的线索 id，检视后计入（P3 归档表用）
- **叙事纪律不变**：只写看到什么；日记只记行为和数字；文本从 `docs/story.md` 原稿取，不另写剧情

### 4.6.5 「时间轴也能检视」到底是什么意思

玩家在**同一个坐标**上，按 Shift 切到时间轴，W/S 让世界从 1926 流到 2026；每停一年按 E，检视的是**那一年这个坐标上的东西**。

| 轴 | 检视时 HUD 显示 | 语义 |
|---|---|---|
| 空间轴 | 物件名 + 当前所见 | "现在这里有这个东西" |
| 时间轴 | 物件名 + **年份** + 当前所见 | "那一年这里有这个东西（当时留下的痕迹）" |

为什么必须这样（这不是装饰，是核心机制）：

1. **时间是门**：玩家站着不动就能读到同一个位置在五个年代的不同记录。若只有空间轴能按 E，时间轴就退化成过场动画，搜证变纯跑图
2. **时间轴玩家没有实体/碰撞**（用户 m00405 定）：所以他能检视空间轴被墙、井、地基挡住的东西——埋在地基下的石磨刻字、井盖下的痕迹，正好对应"真相是物理的"
3. **跨帧对比本身是线索**：A3 尸体和 A4 不在同一位置 → 玩家不需要任何 NPC 告诉他就知道"被人挪过"。归档表填的不是"谁干的"，而是"位置变了 / 年份 / 数量"

防穿帮规则：时间轴检视的文本只描述"那一年看得到的东西"，不能提前泄露后帧才知道的结论（例如 1926 的日记不能写出 1951 才发现的内容）；`axis:"space"` 的证物在时间轴按 E 无反应。

**这条是设计决策，用户可推翻**；目前按"两轴都能检视、时间轴带年份"实现。

### 4.6.6 已知坑（补充 §7）

| 坑 | 后果 |
|---|---|
| 证物图先到、数据没填 | 玩家按 E 没反应，美术白画 |
| `size` 写成 0 但物件实际挡路 | 玩家穿模 |
| 检视热区 < 1 格 | 点不中 / 按 E 判定不稳 |
| `pos`/`texture` 写在全局而不是 `states` 下 | 尸体和日记不会"移动/老化"，故事机制失效 |
| 用 `visible:false` 而不是"该帧没有 state 键" | 对应 HANDOFF §3.3：`visible=false` 不关碰撞，隐藏的证物还会挡路 |
| 贴墙壁画按地面物件做碰撞 | 玩家被看不见的东西挡住 |
| 家具源图高度当占地 | 星露谷立面会多画一格（见 §4.6.2），碰撞区域画大 |
| 时间轴文本提前泄露后续帧结论 | 玩家能在 1926 读到 1951 的发现，搜证崩塌 |

## 4.7 起始帧反转 + 知识门控（2026-11-19 用户拍板，尚未实现）

### 4.7.1 起始帧 = A5，往过去挖

主角从**最晚的时间节点 A5（2026，沈明远什么都不知道）**开局，逐步往过去挖，同时反复切回未来带着新知识重读旧物证。
代码现状：`scripts/timeline.gd:58` 写死 `index = 0`（从 A1 开局），且键位 W=未来 / S=过去。**键位不改**（用户拍板），只把起始帧改成读配置（默认 `a5` / 最后一帧）。

主题从「时间是门」升级为「**知识也是门**」：不是找到新文件，而是带着旧知识重访同一坐标。

### 4.7.2 两套维度分开：客观 states ≠ 主观 discoveries

§4.6.4 的 `states` 是**客观维度**（某帧这东西在哪、长什么样、写着什么）。本节新增的是**主观维度**——主角脑子里知道什么，跨帧**不重置**：

- `discoveries`：全局知识集合，检视触发，切帧不清空
- 证物 state 增加 `unlocks`（检视后解锁哪些知识 id）与 `requires`（需要哪些知识才显示真实内容 / 才可交互）
- 未满足 `requires` 时走「普通外观 + 无提示」分支——**不画灰掉的「？？？」、不给「这里有东西」的暗示**，否则等于剧透

### 4.7.3 暗龛链（最终定稿，取消「施工信息」）

用户拍板：走「链条 3」——**取消施工信息这个概念**，异常靠像素自己说话，零提示牌。房型大变化用户都看得出来，那块砖的异常就藏在「切时间时习惯性对比墙」里。

| 帧 | 暗龛链状态 |
|---|---|
| **A1 1926** | 磨坊是磨坊，**没有暗龛**；真《水簿》沈万山**随身带着**，天天记 |
| **A2 1951** | 账房新砌出暗龛（**新砖色**），里面**空着**——真本仍在沈万山身上。常挪动的那块砖用**第三档颜色**。这是「这地方放过东西」的暗示，不给答案 |
| **A3 1976** | 沈德昌挖地基，真本从**同一个暗龛**出土；玩家的「就是那个位置！」在此兑现。story 5.4 接上：沈德昌看到祖父沈万山的手记，才决定把知情人一起封进地基——真相本身就是凶器 |
| **A5 2026** | 超市门厅上磨盘刻「沈氏丰源·一九五七」。从 A5 开局、已知暗龛和真本的玩家，才读懂这块磨盘的来路 |

随身带真本的人 = **沈万山**（真本停笔 1951 = 他"一个记账的人不记了"那年，story 5.5；1976 沈德昌称之"祖父的手记"，自洽）。

墙壁颜色三档（**全是砖墙、不上油漆**，色差只能是砖本身新旧，不误导成刷漆）：
- 最外侧原墙 = 旧砖色
- A2 新砌的暗龛墙 = 新砖色
- 常挪动的那块砖 = 再单独一档

玩家检视那块砖才给反馈，且**只写看到什么**（例："东数第三块砖，灰缝是新的。按了一下，砖往里陷了半分。"）——是检视后的结果，不是提前引导；暗龛里的东西也不解释来历，让玩家自己把各帧连起来。

## 4.8 室外伪 3D（2026-11-21 用户拍板：投影 / 分层 / 美术拆图）

> 目标：房子有屋顶 + 墙立面、树有树干 + 树冠、玩家绕到家具后面被挡。
> **不动碰撞**（仍是 `frame_data.gd` 的纯数据 AABB），**不动内外 1:1**（§0.1），
> **不动 `_ref/houses/houses_data.json`**。高度不是数据，是绘制约定。

### 4.8.1 投影约定：纯垂直抬升

世界坐标 (x, y) + 高度 z，一律画在 **(x, y − z)**。视点在正南、正交、无透视。

| 选项 | 为什么不选 / 为什么选 |
|---|---|
| 2:1 斜投影（等距） | 要把整张地图（河 / 路 / 田 / 房子）重做成菱形网格，工作量以周计 |
| 真透视 | 与像素对齐冲突，`camera_rig.gd` 的 `position = -offset.floor()` 会抖 |
| **纯垂直抬升** ✅ | 地面图形**一个像素都不用改**，只是把立体物往上挪；像素对齐天然保持 |

代价（接受）：东西两面永远看不到，门窗只能画在南墙。`gate` 本来就全在南墙，不冲突。

**高度常量 `EXTRUDE := 32.0`**（= 一整格，E=32；实测 `scripts/world_view.gd:51`）。写死在代码里，
**不写进 `frames.json`，也不写进 `houses_data.json`**。

> reasons：1926→2026 是同几栋实体房子，高度不随时间变。给了逐帧字段，迟早有人微调成
> 「推时间时房子在呼吸」，并且必然踩 §7 那条「base/roof 尺寸或锚点不同 → 进屋切换屋顶时画面跳动」。
> 立面的高度**绝不能按 lot 比例算**——沈家 A1 lot 20×10、A3 lot 28×21（加晒场），
> 按比例算推时间时房子会越长越高。

### 4.8.2 五层绘制桶（照抄星露谷的结构）

星露谷地图分层（`stardewvalleywiki.com/Modding:Maps`）：`Back` / `Buildings` / `Paths` / `Front` / `AlwaysFront`，
从后到前固定批处理，**真正参与 y 排序的只有 `Front` 一层**。我们照抄这个骨架：

| 桶 | 画什么 | 是否排序 |
|---|---|---|
| `Back` | 地面底色 / 河 / 田 / 路 / 房子 lot 底色 / 房间色块 | 否，固定顺序 |
| `Buildings` | 房子的墙基 + 南立面 + 墙顶面 + 屋顶（整栋当作**一个实体**） | 否，按 `lot.y1` 从小到大 |
| `Paths` | 暂无 | — |
| `Front` | 树 / 家具 / 玩家 / 碑 / 井 | **是，按 `sort_y` 排** |
| `AlwaysFront` | 暗角 / 检视提示 | 否，最后画，永远最上 |

排序键统一按**精灵的底边（脚）**，不是中心：

| 对象 | `sort_y` |
|---|---|
| 玩家 | `position.y + RADIUS * 0.7`（脚下影子那条线，`player.gd` 已有） |
| 树 | `center.y + radius * 0.7` |
| 家具 | 占地 `rect` 的底边 `rect.end.y` |
| 房子 | `lot` 的底边 `lot.y1` |

房子与玩家的排序天然成立，不需要特判：玩家在南边时 `pos.y + 4.9 > lot.y1`（碰撞 probe 半宽 7，
中心离墙至少 7px），在北边必然 `<`。

**注意现有 `player.gd` 的 `z_index = 10` 会变成废字段**，玩家必须作为 `Front` 里的一个条目参与排序，
否则永远是「永远盖住房子」或「永远被房子盖住」。

### 4.8.3 遮挡：整栋房子降 α 到 0.4（照抄星露谷）

> **SUPERSEDED（2026-11-21 用户拍板：不做整栋降 α 0.4；见 `docs/DECIDE-stardew-visual.md` D2）**
> 下面这段只作存档，不要按它实现；现行做法是「进屋不画屋顶 + y-sort 把玩家排到墙前/墙后」。

玩家绕到房子后面被完全挡住时，**把那一栋的绘制透明度降到 0.4**（星露谷默认值就是这个：
`stardewvalleywiki.com` 相关 mod 说明「with the game's default being 0.4」）。降的是**整个实体**
（整栋连屋顶），不是只降被遮的那一块。

```gdscript
var hide_zone := Rect2(lot.position.x, lot.position.y - EXTRUDE, lot.size.x, lot.size.y + EXTRUDE)
if player.sort_y < house.sort_y and hide_zone.intersects(player_body):
    条目 alpha 乘以 0.4
```

两个必须注意的实现点：

1. **α 必须叠在 `_shade()` 之后**。时间轴模式的色差是靠「整个场景重复画三遍」实现的，
   每遍自己会再乘 `alpha_mul`；提前把 0.4 乘进去会闪。
2. 0.4 对平面色块可能偏灰（`WALL_COLOR #8c6b4a` 压在草地 `#6e7a4c` 上会混成脏褐绿）。
   候选值 0.4 / 0.5 / 0.6，**机制不改，只调数字**。

> 这个机制不是可选项：沈家 A3 被完全遮住的区域 448×316 px，比视口高度 360 还高，
> 玩家 60 px/s 横穿要 **5 秒**。硬挡 5 秒是不可接受的。

### 4.8.4 屋顶显示规则（用户 2026-11-21 拍板）

**玩家在建筑占地矩形（`wings`）内 → 不画屋顶；在外面 → 画屋顶。与轴无关，精确判定，不做 α 渐变。**

- 屋顶**不进绘制列表**（不是画成透明），进屋后那 32px 直接不存在。
- 理由：①屋顶挡住的是你自己——时间轴镜头冻结、玩家位置不动，一盖上就失去全部参照；
  ②不为单一轴改规则，否则切轴时屋顶凭空出现 / 消失，撞 §7 那条画面跳动；
  ③不画屋顶正好满足「推时间要能看见外界变化」——房子变成**剖视（娃娃屋）**，
  是全游戏唯一能同时看见「室内随年代变 + 室外随年代变」的视角。

两个陷阱：

1. **必须用当前帧的 `wings` 每帧重算**，不能存一个「进屋了」的布尔开关。沈家 A3 的南厢坐标推到 A1
   是在院子外，那一帧你人就在屋外，屋顶该画回来。
2. **滞回只用在空间轴**（`wings` 外扩 2px 防门槛处闪）；时间轴用精确 `wings`，
   否则会出现「人已经在外面，屋顶却没回来」。

已接受的后果：从大房推到小房时，你站的位置后来变成了院子 → 屋顶「啪」回来盖住你。
不补间，认作设计（房子没了，你被留在露天地里）。

### 4.8.5 美术交付：外观层拆成两图，画布比占地**高一格**

`_house_tex()` 那种「整栋一张图铺满 `lot.size`」的路线**作废**——屋顶要能单独隐藏，
家具要能插到房子中间。外观层必须拆成 `base` + `roof` 两张，且**画布高度比占地多一格
（2026-11-21 TILE 16→32 后，这一格 = **32px**）**：

```
assets/village/houses/<族>/<帧>_base.png   画布 = lot_w × (lot_h + 32) 锚点 = 底部中心
assets/village/houses/<族>/<帧>_roof.png   画布 = lot_w × (lot_h + 32) 锚点 = 底部中心
assets/village/props/<id>.png              画布 = 占地宽 × (占地高 + 立面高)
```

- **多出的 32px 在画布顶部**，是墙和屋顶立起来的高度。画布底边仍与 lot 底边对齐，
  锚点仍是**底部中心**（与既有约定兼容，只是画布高了）。
- 屋顶图里**只有屋本体（`wings`）范围有像素**，院子部分是透明的。
- `base` 与 `roof` **必须同宽同高同锚点，高度都是 `lot_h + 32`**（§7 那条画面跳动）。
  `base` 也要 +32：南立面同样向上溢出，不加高一样被裁。

> 最容易漏的一条：屋顶要向上溢出画布一格。周家 lot 底 y=1472，南立面画在 y∈[1440,1472]，
> 屋顶（z=32）画在 y∈[1280−32, 1440]，屋顶顶端到 1248，而旧画布从 1280 才开始 → **屋顶顶部被裁一条**。
> 不报错、只是少一条，验收时看不出来。

先例：`docs/art-assets-a1a3.md` §5.5 第 1 条自己写着家具「高度可以多画一格」——同一件事。

**影响面**：23 张外观图（12 栋 × 2 层 − 陆家 A3 废墟无 roof）。文件名、目录结构、张数全部不变，
只改 `_ref/houses/gen_asset_breakdown.py` 的尺寸公式并重跑。

### 4.8.5b 显示方案（2026-11-21 TILE 32 配套，方案一）

用户要求：**一格看起来和 16px 时代一样大，只是精度翻倍**。这决定了整套显示参数：

| 项 | 值 | 为什么 |
|---|---|---|
| 逻辑视口 | **1280×720** | 640×360 × 2。视野仍是 **40 × 22.5 格**，与旧版完全一致 |
| 窗口 | 1280×720（1×） | 不变。别和视口混淆：视口是游戏画布，窗口是屏幕占用 |
| `stretch/scale_mode` | **`0` = fractional** | 🔴 关键。1=integer 在 1080p 会把 1.5× **向下取整成 1×**，游戏只占屏幕 44%、四周 56% 黑边，且格子反而缩到 32px（比旧版 48px 更小） |
| `stretch/mode` | `canvas_items` | 文字按屏幕分辨率渲染，非整数缩放下比 `viewport` 清晰 |
| `stretch/aspect` | `keep` | 16:9 屏上等价于 expand；超宽屏先保视野确定 |
| 窗口模式 | `EXCLUSIVE_FULLSCREEN` | 普通 Fullscreen 会在底部留 1px，把整数缩放挤掉一档 |

**为什么必须是 fractional**：一格的物理尺寸 = 32 × 缩放倍数。要让它在各分辨率下与 16px 时代（16 × N）**完全相等**，倍数必须是 N/2：

| 分辨率 | 旧：16px × N | 新：32px × (N/2) | 格子物理尺寸 | 是否一致 |
|---|---|---|---|---|
| 1280×720 | 16 × 2 = 32 | 32 × 1.0 = 32 | 32 px | ✅ |
| 1920×1080 | 16 × 3 = 48 | 32 × **1.5** = 48 | 48 px | ✅ |
| 2560×1440 | 16 × 4 = 64 | 32 × **2.0** = 64 | 64 px | ✅ |
| 3840×2160 | 16 × 6 = 96 | 32 × **3.0** = 96 | 96 px | ✅ |

1440p 和 4K 上算出来正好是 2.0 和 3.0，**渲染结果与 integer 模式完全相同**，不牺牲任何画质。
唯一有代价的是 1080p 的 1.5×：横向滚动时竖线会轻微"忽粗忽细"。这是「格子大小恒定」的数学必然
（1080p 宽 1920 ÷ 40 格 = 48px/格，48 不是 32 的整数倍）。缓解手段是换线性过滤，但那会让像素画发糊，
与「要精度」的初衷冲突，**不采用**。

**HUD 坐标系**：`scripts/hud.gd` 里所有数字都是 640×360 时代的设计值，统一乘 `UI` 常量（现在是 2.0）。
改视口只需改 `UI`，坐标表一个字都不用动。

### 4.8.6 坑表（补充 §7）

| 坑 | 后果 |
|---|---|
| 屋顶画布不带顶部 32px 溢出 | 屋顶被裁一条，不报错，验收看不出来 |
| 立面高度按 lot 比例算 | 推时间时房子越长越高（沈家 A1→A3） |
| 给 `frames.json` 加逐帧 `roof_height` | 被微调成「房子在呼吸」，且破坏 base/roof 同锚点 |
| 玩家留在 `z_index = 10` | 绕到房子后面仍画在屋顶上，伪 3D 直接失效 |
| 遮挡 α 在 `_shade()` 之前乘 | 时间轴三遍重绘各自再乘一次，画面闪 |
| 屋顶用 α 渐变淡出 | 半透明屋顶叠在半透明室内上，糊成一团；且违反 §4.8.4「无渐变」 |

| 忘记把连续墙格合并成矩形 | Web 导出（`gl_compatibility`）掉帧 |

## 8. 待办：楼层与穿墙（2026-11-19 用户拍板，尚未实现）

> 本节是**设计决议 + 排期**，不是已完成的机制。代码现状仍是纯 2D（`frame_data.gd` 的 `is_free()` 只有 AABB，无高度维度），推时间会被目标帧 solid「顶住」（`timeline.gd:84-88`）。

### 8.1 走方案 C「表面高度快照」，不学星露谷的 warp 换地图

- 星露谷进建筑/上楼 = 黑屏 warp 到独立地图、坐标重置（`stardewvalleywiki.com/Modding:Maps`）。**不用**：会砸掉本项目三条核心机制——内外严格 1:1、同坐标跨五帧、时间轴无碰撞。
- 方案 C 做法：每帧加可选 `surface`（矩形 + 高度 z）；玩家加高度状态；推时间时查「目标帧该坐标**不高于当前高度**的最高可站表面」并落上去；绘制按高度抬 y。
- 只碰时间轴；空间轴移动继续用原来的 2D 墙判定，不推倒重来。
- 改动范围：`scripts/frame_data.gd`（surface 查询）、`scripts/timeline.gd`（`step_time()` 语义）、`scripts/player.gd`（高度状态 + 绘制抬升）、`data/frames.json`（surface 字段）。
- 复用 §4.6.4 已定稿的逐帧 `states` 结构（高度也是逐帧状态的一种）。

### 8.2 屋顶必须有线索（用户设计口径）

- 用户 m01214：「如果能站在屋顶上，那么屋顶上应该也要有线索，不然单纯多个功能太突兀了。」
- 即**楼层变化是搜证内容的一部分**，不是纯技术展示。屋顶/新加盖楼层要放证物（逐帧 states），例：沈家 2001 加建那一翼的屋顶有施工标记、账本残页等，推到那一年站上去才检视得到。
- 屋顶线索文本遵守 §4.6.5 防穿帮规则（不泄露后帧结论）。

### 8.3 卡墙虚化 = 主题机制，不是穿帮（用户设计口径）

- 用户 m01214：主角是游离于世界之外的人，「被墙遗忘」合理 → 会出现**建模与墙重合、主角虚化**的现象。
- 具体场景：在二楼推时间，目标帧该坐标无合适表面且落在墙体/建筑占地内 → 不 bump，而是进入 **phasing（虚化）状态**。
  - **往里走**（朝建筑中心方向位移）→ 落到室内地面，屋顶淡出（复用 §4.5 室内三层方案）→「进屋子」。
  - **往外走**（离开建筑占地矩形）→ 落到室外地面 →「落到地上」。
- 视觉：半透明（建议 alpha≈0.4）+ 轻微色差，强化「被墙遗忘」。
- 实现约定：新增 phasing 状态；时间轴原本 A/D 无作用，**仅在 phasing 状态下临时启用 A/D 做内/外位移**，不改正常时间轴的 W/S 推年份手感。
- ⚠️ **phasing 期间必须绕过 `is_free()`**（2026-11-21 补，代码没写、文档之前也没写）：
  phasing 时 `char_pos` 正好落在目标帧的 `solid_rects` 里，`move_space()` → `is_walkable()` →
  `frames[i].is_free(at)` 会一直返回 `false`，**一步都挪不动**，启用了 A/D 也没用。
  正确做法：phasing 走独立位移路径，直接改 `char_pos` 不查 `is_free`；每步结束用
  `if frames[index].is_free(char_pos): 退出 phasing` —— `is_free` 的角色从「能不能走」变成「出没出去」。
- 排期：跟 8.1 方案 C 同期实现（C 的「查不到表面」分支就是 phasing 入口），不要单独提前。

### 8.4 时间账与排序

- 距截止 2026-12-01 13:37 PST（北京 12/02 05:37）约 12 天半。
- 估算：方案 C 约 1.5–2.5 天 + phasing 虚化约 0.5–1 天 + 屋顶线索内容约 0.5 天 ≈ **2.5–4 天**（前提是室内数据结构先定稿）。
